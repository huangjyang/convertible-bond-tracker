# 2026-09-20

## 需求: 能不能用 LangGraph 做一个"主动解读市场"的智能体(信息主动找我)

**用户设想:** 盘中(如 9-10 点)自动解读"某行业流入资金多少、受追捧、很热", 给出对应值得关注的可转债;
定位是"保姆" —— 主动告知当前什么信息重要, 降低找信息的成本。动机来自看到 OpenMAIC(多智能体交互课程)用 LangGraph。

**给出的判断(结论): 方向对, 但 LangGraph 放错了因果链位置。**
- 项目已有全市场采集/放量扫描/蓄势分+点火+追高分层回测/159 项测试 —— 这是最难最值钱的一层, 已完成。
- 真正缺的三样, LangGraph 一个都不解决: ①盘中数据(现为 15:30 收盘后 + 打开页面触发) ②板块资金流(原本完全没有) ③推送通道(只有本机 8734 网页)。
- LangGraph 真正值钱处: checkpointer 持久化"今天推过什么"、interrupt 人工确认、条件路由。属**最后加的编排层**。
- 建议顺序: 先用普通 Python 函数把 pipeline 写通, 节点边界清晰后再套 LangGraph 是机械劳动(半小时); 反过来先套框架会把时间花在调框架上。
- 真正的 agent 价值在"多轮追问"(这几只哪个风险小/为什么排除 XX), 那时才需要 agent loop + 工具调用。**把"主动推送"(workflow)和"交互追问"(agent)当成两个东西。**
- OpenMAIC 类比的问题: 课程生成无实时性、无数字正确性硬约束; 市场解读两者都是硬约束。借鉴多 agent 分工可以, 借鉴"让 LLM 自由生成"不行。

**三个陷阱(已用项目自身数据论证):**
1. 信息过载 = 又一个信息源。蓄势研究已证明严蓄势后 5 日内爆发概率仅 0.9%(全样本 11%) → 绝大多数时候正确动作是**什么都不说**。
2. 时效幻觉: 等资金流显示"流入 50 亿"往往已涨完。自家回测佐证: 高位爆发 T+20 −3.18%/胜率 27%, 低位点火 +0.70%/最大浮亏 −1.81% → 推送应基于**前瞻信号 + 风险告警**, 不是追涨。
3. 别让 LLM 算数: 数字必须来自代码, LLM 只做排序理由与文字。否则得到通顺但数字错误的简报, 比没有更危险。

### 映射结论(推翻了工作区里的一个初始假设)
- 转债记录的 `industry`(东财 f127) 与板块名**同属申万分类体系** → 按**名称精确匹配**即可。
- **不需要手写映射表。** 板块名 496 个无重名, 匹配无歧义。
- 初始基于历史快照以为"只有 30 个 distinct industry, 手写 30 行就够" —— **错了**:
  历史快照只含每日成交额 Top30, 看不到长尾。**完整宇宙是 85 个 distinct 行业, 85/85 全部可解析**
  (如 `电网设备` 就不在那 30 个里)。手写 30 行会漏掉 55 个(约 65%)。
- 已把"完整映射全部可解析"写成测试断言, 并断言 `行业数(85) > 30` 来固化这个反例。

### 关键设计决定
1. **每只转债只归属唯一一个板块**, 不做任何加总 → 从结构上杜绝跨层重复计数。
2. **未映射的券绝不静默丢弃** → 进 `unmapped` 并打警告(测试断言 `hits+unmapped` 守恒)。
3. **`live` 标志: 非交易时段数据不是当日实时进度, 推送前必须检查。**
   实测今天(09-20 周日)跑出来 `session=休市, live=False` —— 若不看这个标志, 会把**周五收盘**的资金流
   当成"刚刚流入 182 亿"推出去。`session_of()` 不认法定节假日(只看周末), 但节假日会判成"盘前", live 仍为 False, 方向安全。
4. 时点重复保护: 与上一时点间隔 < 60s → **覆盖**而非追加(实测验证); 每天最多留 60 个时点。
5. 时点内每只券只留 `code/name/price/chg/turnover_yi/premium/stock_chg`。
   原本存全字段 = 78KB/时点 → 满一天 48 时点约 3.7MB; 精简后 **54.5KB/时点 ≈ 2.6MB/天**
   (与既有单个日频文件 1.2~1.8MB 同量级)。慢变字段(stock_name/redeem_trigger/评级)放映射缓存与既有日频快照。
6. **映射漂移检测**: 缓存里的 board_code 与实时名录不符 → 报告(东财改板块代码是真实风险)。

### ⚠ 预先存在的测试失败(不是本次改动引起, 已用对照实验确证)
`voltab_smoke` 失败 1 项、`qijin_pending_smoke` 失败 4 项。
- **对照实验**: 把本次新增的 3 个 data 文件移出 `data/` 后重跑 → **失败完全相同** ⇒ 与本次改动无关。
- 相关数据文件 mtime 全是 `09-18 18:22`, 而本会话是 `09-20 07:4x` ⇒ 数据早于本次会话就已变成这样。
- **根因**: 这两套测试把断言写死到具体数据状态(`已完成数 = 346`、`09-14 进表的仍是 6 行`、
  `09-14 上限`、`20/30 只 ≥80 根`)。09-18 18:22 数据刷新补齐了 09-18 的 K 线后计数漂移, 断言即失效
  (实测: 346→352, 已完成最新日期 09-14→09-15)。
- 另: `coil_smoke` / `bond_detail_smoke` 全部通过。
- **待办**: 这两套的断言该改成"性质断言"(如: 已完成数 ≥ 上次、最新已完成日期随K线推进而前移、
  被标数据不足的券必须都能在K线里找到)而不是写死数字。**需用户决定后再改。**

**确认新文件不会与既有日期发现逻辑冲突**: `app.py` 用 `re.match(r"\d{4}-\d{2}-\d{2}\.json$", f)`
(行首锚定), `sector_flow_2026-09-20.json` 以 `sector_flow_` 开头不会误匹配; 也无人调用 `_newest_file_date("sector_flow")`。
